# Alma Intra — agent conventions

Alma Intra is the internal system of Alma: customers and their contacts, personalised e-mails to
customers from editable templates, files, activities and replies, all in one place. It is a
separate app from Alma ADOS and reuses its stack, design and components. This file is the contract
for every AI agent and human working in this repo. What the app does is in
`docs/functional-spec.md` (decisions D-1…D-31); the screen designs are in `docs/design/`.

## Language

- Code, identifiers, comments, commit messages, docs in `docs/`, Jira and PR descriptions:
  **English only**. Quote Slovak UI copy in „…“ where needed.
- Slovak appears only in UI strings (`packages/shared/src/i18n/sk.ts`) and the system e-mails.
- UI copy joins no two thoughts with a dash: use a full stop, a comma or a colon. A dash is only for
  ranges, written without spaces („8:00–9:30“), or alone as the mark of an empty value. No screen
  or ticket codes and no notes about the project in strings. Copy is gender neutral.

## Stack (do not swap without a recorded decision)

- TypeScript everywhere. pnpm workspaces + Turborepo.
- `apps/api` — NestJS modular monolith, tRPC, Drizzle ORM, PostgreSQL 16, transactional mail outbox
  (Resend). In production it also serves the built web (`WEB_DIST_DIR`).
- `apps/web` — Vite + React SPA, TanStack Router, React Query via tRPC, Zustand (UI state only),
  React Hook Form + Zod, shadcn/ui + Tailwind 4.
- `packages/shared` — Zod schemas, `can()` authorization, i18n. Web and API import its built
  output: run `pnpm --filter @intra/shared build` after changing it.

## Non-negotiable rules

1. **One role.** Every user is `admin`; the first user is created by the CLI
   (`create-first-user`) and invites the others. Permission checks still go through `can()` from
   `packages/shared`, never ad hoc, so a second role can come later.
2. **Two-step verification is mandatory.** No session exists without a confirmed TOTP factor;
   a password alone never signs anybody in.
3. **Audit.** Mutations and sensitive reads are logged by the audit interceptor into append-only
   `audit_events`. Never write audit rows by hand; `intra_app` cannot update or delete them.
4. **Two DB roles.** Migrations run as `intra_admin`; the server runs as `intra_app` and never gets
   the admin URL.
5. **Secrets stay secret.** TOTP secrets are encrypted at rest (`DATA_ENCRYPTION_KEY`); tokens live
   in httpOnly cookies; one-time tokens travel in the URL fragment and POST bodies, never a query
   string. Log ids, never e-mails or free text.
6. **Migrations** are generated by Drizzle and reviewed by a human. Never edit an applied migration.

## Local development

```bash
pnpm install
docker compose up -d postgres s3     # Postgres 16 on :5434, S3 (SeaweedFS) on :8333
cp .env.example .env                 # then set DATA_ENCRYPTION_KEY
pnpm --filter @intra/shared build
pnpm db:migrate && pnpm db:seed
pnpm dev                             # API on :3100, web on :5180
```

The seed signs in as `jana.horvathova@example.com` / `Alma-intra-2026`; its TOTP secret is
`JBSWY3DPEHPK3PXP` (dev only). Production starts empty: `pnpm --filter @intra/api
users:create-first -- --email <e-mail> --name "<name>"` (in the image:
`node dist/db/create-first-user.cli.js --email … --name …`) creates the first account and e-mails
its invitation.

## Checks before a PR

`pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test`, `pnpm build`, and
`pnpm test:integration` (Testcontainers, needs Docker). CI runs the same, plus the production
image build (`apps/api/Dockerfile`).
